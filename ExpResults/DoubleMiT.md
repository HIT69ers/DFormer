# DoubleMiT实验记录

## 网络结构

### BaseLine

![CMX](E:/Files\DFormer\ExpResults\fig\DoubleMiT.png)

Downsample和Upsample均采用双线性插值实现；

1. $Dounsample$用于将图像或feature map下采样一定倍率：
    $$
    F_{out}=Downsample(F_{in}), \\[4pt]
    F_{in}\in R^{C\times H\times W}，F_{out}\in R^{C\times \gamma H\times \gamma W}, \gamma \in [0.5,0.6,0.7,0.8,0.9,1.0]
    $$
2. $Upsample$用于将feature map上采样一定倍率：
    $$
    F_{out}=Upsample(F_{in}), \\[4pt]
    F_{in}\in R^{C\times \gamma H\times \gamma W}, F_{out}\in R^{C\times H\times W}，\gamma \in [0.5,0.6,0.7,0.8,0.9,1.0]
    $$
3. 对RGB数据和Depth数据采用非对称backbone可能会导致同一个layer输出特征的通道数不一致，因此采用$1\times1Conv$用于对齐通道；

## 分析与疑惑

关于训练：

1. 评估若采用多尺度，单次评估的平均时间约为220s；改为单尺度后，降低为约180s；但仍然很慢，因为训练阶段单个epoch的平均时间不超过30s；
2. 对评估阶段的各段代码花费时间进行了测量，发现主要慢在这一步：

    ```python
    images = minibatch["data"].cuda()
    ```

    但是在cuda()中将non_blocking设为True并不能提高整体评估效率；
3. 为了减少评估所需时间，进行了以下尝试，但均无明显效果：
    3.1. 改变评估时的batch_size；
    3.2. 使用另外的cuda.Stream()分离出评估时的数据加载任务；
    3.3. 将DataLoader的num_workers由16调整为8；
    3.4. 删去完成一轮epoch后、转入评估阶段之前的torch.cuda.empty_cache()；

关于测速：

1. 该文档记录的测速数据均在服务器无其他任务时完成，但对同一backbone的相同分辨率降低比，测速结果仍有明显波动；
2. 上一次的测速脚本中没有model.eval()这一步操作，导致整体结果偏慢；
3. 只测出了变backbone时的推理速度变化，未测出变分辨率时的速度变化；
4. 尝试另写了一个测速脚本，把送入model的数据从随机初始化的数据变为数据集中的数据，测得的帧率明显降低，显然未排除数据加载时间的干扰；
